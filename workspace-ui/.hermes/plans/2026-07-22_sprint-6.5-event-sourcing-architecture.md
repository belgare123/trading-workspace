# Sprint 6.5 — Deterministic Event Sourcing Architecture

> **Status:** Draft for review  
> **Date:** 2026-07-22  
> **Authors:** Виталий (Architecture), Hermes Agent  
> **Prerequisites:** ✅ Sprint 6.4 (OTel/Prometheus Export Layer)  

## Goal

Построить детерминированную систему event sourcing поверх существующего EventBus, обеспечивающую:
- Воспроизводимое восстановление состояния любого Runtime после сбоя
- Расследование инцидентов: «что именно произошло в этом трейде»
- Регрессионное тестирование на реальных данных
- Аудит и экспорт журналов для внешних систем

## Architecture Decision Records

### ADR-1: Storage Backend — SQLite (better-sqlite3)

**Решение:** SQLite (better-sqlite3) — основной backend для EventJournal.

**Обоснование:**
- ACID — журнал не потеряется при аварийном завершении
- Индексы — быстрый replay по tradeId, traceId, timestamp, eventType
- Один файл — легко копировать вместе с workspace
- Нет внешней инфраструктуры
- Производительности достаточно для одного торгового инстанса

**JSONL (JSON Lines)** — только как формат экспорта для расследования инцидентов.
**PostgreSQL** — отдельный backend через IEventJournal, когда появится необходимость в распределённой архитектуре.

### ADR-2: EventJournal — единый компонент

Не просто журнал событий, а журнал + снапшоты:

```
EventJournal
├── events
├── snapshots
├── replay
├── prune
└── export
```

### ADR-3: Two SQLite tables

**events:**
| Column | Type | Notes |
|--------|------|-------|
| id | TEXT | UUIDv7 |
| sequence | INTEGER | AUTOINCREMENT |
| timestamp | INTEGER | UTC ms |
| traceId | TEXT | |
| tradeId | TEXT | для быстрой фильтрации по сделке |
| runtime | TEXT | RuntimeId |
| eventType | TEXT | |
| payload | TEXT | JSON |
| metadata | TEXT | JSON (version, source, schemaVersion) |

Indexes: tradeId, traceId, timestamp, sequence, eventType

**snapshots:**
| Column | Type | Notes |
|--------|------|-------|
| tradeId | TEXT | PK |
| sequence | INTEGER | последнего события |
| snapshot | TEXT | JSON |
| createdAt | INTEGER | UTC ms |
| stateHash | TEXT | SHA256 |

### ADR-4: Schema versioning с первого дня

Каждый EventEnvelope содержит `metadata.schemaVersion`.
ReplayEngine проверяет совместимость версий.
Изменения модели не ломают старые журналы.

### ADR-5: SnapshotManager — в первой версии

SnapshotManager встроен в EventJournal с первого дня.
Восстановление: Snapshot #5200 → Events 5201..N → Current State.
Вместо replay всех 5200 событий.

PostgreSQL backend может быть реализован позже без изменений ReplayEngine/SnapshotManager.

### ADR-7: Write model — гибридный flush

**Решение:** Гибридная политика — обычные события батчами, критические с немедленным fsync.

```typescript
interface JournalFlushConfig {
    maxBufferedEvents: number           // 50 — fsync после N обычных событий
    maxFlushIntervalMs: number          // 100 — fsync по таймеру
    flushOnTradeClosed: boolean         // true
    flushOnSnapshot: boolean            // true
    flushOnShutdown: boolean            // true
    flushOnEmergencyStop: boolean       // true
    flushOnKillSwitch: boolean          // true
    synchronousCriticalEvents: boolean  // true
}
```

**Критические события** (немедленный fsync после append):
- OrderSubmitted, OrderAccepted, OrderFilled
- PositionOpened, PositionClosed
- WalletCommitted, WalletWithdrawn
- RecoverySnapshot, KillSwitchActivated

**Обычные события** (батчевый flush):
- MarketTick, IndicatorUpdated
- Telemetry, Metrics, Health

**SQLite PRAGMA:**
- `journal_mode=WAL` — Write-Ahead Log
- `synchronous=NORMAL` (default) / `FULL` (configurable for production)
- `busy_timeout=5000`

**Поток:**
```
MarketTick → buffer → flush later
OrderFilled → append → fsync immediately → done
```

### ADR-8: Retention policy — гибрид (горячий + холодный слой)

**Решение:** Трёхуровневая политика хранения с автоматическим архивированием.

```typescript
interface RetentionPolicy {
    fullJournalDays: number              // 30 — горячий слой
    keepSnapshots: number                // 100 — последних
    archiveMetadataForever: boolean      // true — история сделок навсегда
    compressArchivedJournal: boolean     // true — gzip/SQLite
    pruneOnStartup: boolean              // false
    pruneDaily: boolean                  // true
}
```

**Горячий слой (30 дней):**
- Полный EventJournal — все события, replay любой даты
- Одна SQLite БД (`journal.db`)

**Средний слой (snapshots):**
- Последние 100 snapshot'ов (запас при повреждении последнего)
- Откат на N-1, N-2... если последний повреждён

**Холодный слой (архив):**
- После 30 дней: `journal-2026-07.sqlite` → gzip → `archive/`
- Удаляются: MarketTick, Heartbeat, Telemetry, Metrics, HealthSnapshot, IndicatorCalculated
- **Хранятся бессрочно:** TradeOpened, TradeClosed, OrderFilled, OrderRejected, WalletCommit, Recovery, KillSwitch, EmergencyStop, ConfigurationChange, ManualOverride
- Агрегированная история (TradeHistory, PnL, Orders, Recovery Reports, Certification Reports, Alert History, SLO History) → `metadata.db`

**Разделение БД:**
```
journal.db          — горячий журнал (30 дней)
archive/
  2026-07.sqlite.gz
  2026-08.sqlite.gz
metadata.db         — вечная аналитика
```

**Очистка:** раз в сутки фоновым процессом.

**Что никогда не удалять:**
- TradeOpened, TradeClosed — история торговли
- OrderFilled, OrderRejected — исполнение
- WalletCommit — движение средств
- Recovery — восстановление
- KillSwitch, EmergencyStop — события безопасности
- ConfigurationChange, ManualOverride — аудит действий

**Что можно удалять после 30 дней:**
- MarketTick, Heartbeat — сырой рынок
- Telemetry, Metrics, HealthSnapshot — агрегировано в metadata.db

```

        │
        ▼
JournalWriter
        │
        ▼
IEventJournal ←── SQLiteEventJournal (better-sqlite3)
        │
 ┌──────┴──────────┐
 ▼                 ▼
SnapshotManager    ReplayEngine
        │                 │
        └────────► RecoveryRuntime
                        │
                        ▼
                 EventBus.publish()
                        │
                        ▼
                 Runtime слушает и восстанавливает состояние

Export:
IEventJournal.exportJSONL() → incident-2026-07-22.jsonl
```

```
Runtime
   ↓ publish()
EventBus
   ↓ intercept()
EventJournal (append-only)
   ↓
Storage
```

**Replay:**
```
Storage
   ↓
ReplayEngine → EventEnvelope[]
   ↓
EventBus.publish()
   ↓
Runtime слушает и восстанавливает состояние
```

**Snapshot + Replay:**
```
Snapshot (Trade, Wallet, Risk, Orders...)
   +
Events after snapshot (№ 251..310)
   ↓
ReplayEngine
   ↓
StateRebuilder → Full state
```

## Non-negotiable principles

1. **EventJournal — единственный writer.** Ни один Runtime не пишет напрямую в storage.
2. **ReplayEngine не знает о Trade.** Он знает только Journal → Envelope → EventBus.publish().
3. **Каждое событие immutable.** После записи — не изменяется.
4. **EventEnvelope — единый формат.** Абсолютно каждое событие проходит через него.
5. **Versioning с первого дня.** `version: 1` закладывается в envelope.

## 6.5.1 EventEnvelope — единый конверт событий

### Interface

```typescript
type RuntimeId = 'gateway' | 'trade' | 'wallet' | 'risk' | 'strategy'
               | 'ordermanager' | 'exit' | 'feed' | 'telemetry' | 'system'

interface EventEnvelope<T = unknown> {
    /** Уникальный ID события (UUIDv7 — сортируемый по времени) */
    id: string

    /** Trace ID для связывания событий одного сценария */
    traceId: string

    /** ID вызвавшего события (parent event) */
    causationId?: string

    /** Correlation ID для группировки событий одного бизнес-процесса */
    correlationId?: string

    /** Trade ID для быстрой фильтрации по сделке */
    tradeId?: string

    /** Имя Runtime-компонента-источника */
    runtime: RuntimeId

    /** Тип события (доменное имя, напр. 'TradeOpened', 'OrderFilled') */
    type: string

    /** Порядковый номер в Journal (sequence number) */
    sequence: number

    /** Timestamp создания (UTC ms) */
    timestamp: number

    /** Полезная нагрузка — собственно данные события */
    payload: T

    /** Служебные метаданные */
    metadata: {
        version: 1           // версия конверта
        schemaVersion: 1     // версия схемы payload
        source: string       // например 'workspace-ui:1.2.3'
    }
}
```

### Properties

- **immutable** — поля не меняются после создания
- **versioned** — `metadata.version` позволяет эволюционировать формат
- **сериализуемый** — JSON (плоский, без циклических ссылок)
- **пригодный для replay** — вся информация для воспроизведения есть в конверте

### Discussion points

- UUIDv7 vs UUIDv4 — UUIDv7 даёт временну́ю сортировку, полезно для Journal
- Размер `metadata` — минимальный, только то, что нужно всем
- `causationId` vs `correlationId` — causationId = parent chain, correlationId = бизнес-группировка

## 6.5.2 EventJournal — единый writer

### Interface

```typescript
interface IEventJournal {
    /** Append событие (атомарно, возвращает sequence) */
    append(envelope: Omit<EventEnvelope, 'sequence'>): Promise<EventEnvelope>

    /** Flush буферизованные записи на диск */
    flush(): Promise<void>

    /** Rotate — закрыть текущий сегмент, начать новый */
    rotate(): Promise<void>

    /** Создать snapshot текущего состояния Journal (мета-информация) */
    snapshot(): Promise<JournalSnapshot>

    /** Recovery после старта — проверить целостность */
    recover(): Promise<JournalRecoveryResult>

    /** Read events by filter (для ReplayEngine) */
    read(filter?: JournalFilter): AsyncIterable<EventEnvelope>

    /** Get current sequence number */
    getCurrentSequence(): number
}
```

### Storage backends (обсудить)

| Backend | Pros | Cons |
|---------|------|------|
| **File (JSON lines)** | Простота, читаемость, git-friendly | Нет индексов, медленный read по фильтрам |
| **SQLite** | Индексы, фильтры, встроен в Node.js через better-sqlite3 | Двоичный формат, сложнее inspect |
| **RocksDB (leveldb)** | Высокая производительность, embeddable | Нативная сборка, сложнее на Windows |
| **PostgreSQL** | LN, репликация, знаком всем | Требует внешнего сервиса |

### Filter for read()

```typescript
interface JournalFilter {
    runtime?: RuntimeId
    type?: string | string[]
    traceId?: string
    correlationId?: string
    afterSequence?: number
    beforeSequence?: number
    afterTimestamp?: number
    beforeTimestamp?: number
    limit?: number
}
```

### Discussion points

- **Segments** — journal разбивается на сегменты (по времени или размеру) для ротации
- **Sync mode** — каждое append может быть sync (ждёт fsync) или async (buffer → batch fsync)
- **Integrity** — SHA256 чексуммы на каждый сегмент

## + SnapshotManager

### Interface

```typescript
interface ISnapshotManager {
    takeSnapshot(): Promise<Snapshot>
    loadLatest(tradeId?: string): Promise<Snapshot | null>
    loadAtSequence(sequence: number): Promise<Snapshot | null>
    listSnapshots(): Promise<SnapshotMeta[]>
    prune(keepLast: number): Promise<void>
}
```

### Policy (адаптивный алгоритм v1.0)

```typescript
interface SnapshotPolicy {
    maxEvents: number          // 100
    maxIntervalMs: number      // 5 * 60_000
    snapshotOnTradeClose: boolean      // true
    snapshotOnPositionChange: boolean  // true
    snapshotOnShutdown: boolean        // true
    onlyWhenDirty: boolean             // true
}
```

Условия создания snapshot — выполнение ЛЮБОГО:

| Условие | Значение | Почему |
|---------|----------|--------|
| maxEvents | 100 | Высокая активность — не ждать 5 мин |
| maxIntervalMs | 5 мин | Низкая активность — не replay часы |
| trade closed | ✅ | Естественная точка консистентности |
| position changed | ✅ | Ключевое состояние |
| shutdown | ✅ | Graceful stop → snapshot |
| onlyWhenDirty | ✅ | Нет snapshot без изменений |

**Dirty flag:**
```
dirty = false
onEvent() → dirty = true
timer() → if (dirty) snapshot(), dirty = false
shutdown → flush journal, snapshot(), exit
```

### Snapshot structure

```typescript
interface Snapshot {
    id: string
    sequence: number        // sequence последнего события в Journal
    timestamp: number
    runtime: RuntimeId

    state: {
        trades: Record<string, TradeState>         // открытые/закрытые сделки
        wallet: WalletState                         // балансы
        risks: RiskEngineState                      // risk checks
        strategy: StrategyState[]                   // active strategies
        orders: Record<string, OrderState>         // активные ордера
        gateway: GatewayState                       // подключения
    }

    /** SHA256 хеш состояния (StateHasher) */
    stateHash: string

    /** Версия формата snapshot */
    version: number
}
```

### Strategy

- Snapshot создаётся **периодически** (например, каждые 100 событий или каждые 5 минут)
- Также snapshot создаётся **перед критическими операциями** (старт, стоп, deploy)
- Хранится **тот же storage**, что и Journal (или отдельный)

## 6.5.4 ReplayEngine

### Core rule

> ReplayEngine не знает ничего о Trade, Wallet, Risk, Orders.  
> Он знает только Journal → Envelope → EventBus.publish().

### Interface

```typescript
interface IReplayEngine {
    /** Полный replay — snapshot + последующие события */
    replayFull(): Promise<ReplayResult>

    /** Replay одной сделки */
    replayTrade(tradeId: string): Promise<ReplayResult>

    /** Replay одного Runtime */
    replayRuntime(runtime: RuntimeId): Promise<ReplayResult>

    /** Replay одной стратегии */
    replayStrategy(strategyId: string): Promise<ReplayResult>

    /** Replay за период */
    replayTimeRange(from: number, to: number): Promise<ReplayResult>

    /** Replay по traceId (один сценарий) */
    replayTrace(traceId: string): Promise<ReplayResult>

    /** Replay после timestamp */
    replayAfter(timestamp: number): Promise<ReplayResult>

    /** Replay до timestamp */
    replayBefore(timestamp: number): Promise<ReplayResult>
}
```

### Speed control

```typescript
type ReplaySpeed =
    | { mode: 'realtime' }
    | { mode: 'fast', multiplier: 10 | 100 }
    | { mode: 'step' }       // next() / pause()
    | { mode: 'instant' }    // максимально быстро

interface InteractiveReplay {
    next(): Promise<EventEnvelope | null>
    pause(): void
    resume(): void
    stepOver(count: number): Promise<EventEnvelope[]>
    seek(sequence: number): Promise<void>
}
```

### StateRebuilder

```
Snapshot (sequence=250)
   ↓
Events 251, 252, ... 310
   ↓
ReplayEngine.publish(event) for each
   ↓
StateRebuilder слушает EventBus → обновляет Runtime
   ↓
Full state verified
```

## 6.5.5 ReplayValidator

### Purpose

После replay сравнить ожидаемое состояние с фактическим.

```typescript
interface IReplayValidator {
    validate(snapshot: Snapshot, afterReplay: CurrentState): Promise<ValidationResult>
}

interface ValidationResult {
    overall: 'PASS' | 'DIFF'
    checks: {
        wallet: { expected: string, actual: string, match: boolean }
        trades: { expected: string, actual: string, match: boolean }
        orders: { expected: string, actual: string, match: boolean }
        positions: { expected: string, actual: string, match: boolean }
